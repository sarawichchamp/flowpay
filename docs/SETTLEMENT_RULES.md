# Settlement Rules

เอกสารนี้เป็นบันทึกกติกา settlement ของโปรเจกต์ FlowPay เพื่อใช้เป็น source of truth ร่วมกัน

- ใช้สำหรับอธิบายว่าแต่ละยอดในหน้า `settlement` มาจากอะไร
- ใช้เป็นเกณฑ์เช็กว่า logic ในระบบยังตรงกับที่ตกลงกันหรือไม่
- ถ้ามีการเปลี่ยนกติกาธุรกิจในอนาคต ต้องแก้เอกสารนี้พร้อมกับ code

## 1. แนวคิดหลัก

ระบบนี้คำนวณ settlement ของคน 2 คนในแต่ละรอบบิล โดยเอารายการทั้งหมดของรอบนั้นมารวมเป็น 2 ฝั่ง

- `A ให้ B`
- `B ให้ A`

จากนั้นเอา 2 ฝั่งมาหักลบกัน เพื่อได้ยอดโอนสุทธิจริงแค่ครั้งเดียว

ตัวอย่าง

- ถ้า `Champ ให้ Lily = 10,115`
- และ `Lily ให้ Champ = 21,626`
- ยอดโอนสุทธิจะเป็น `Lily ให้ Champ = 11,511`

## 2. คำที่ใช้ในระบบ

### 2.1 คนถือกระเป๋าอาหาร

คือคนที่เป็นเจ้าของกระเป๋าอาหารของรอบนั้น

- ค่าอาหารควรถูกจ่ายจากกระเป๋านี้เป็นหลัก
- ถ้ามีอีกคนจ่ายแทน ระบบจะมองว่าเป็นการจ่ายแทนกระเป๋า

### 2.2 ค่าอาหาร

คือรายการ `transactionType = food`

### 2.3 ค่าใช้จ่ายร่วม

คือรายการที่ต้องหารกันคนละครึ่ง

- ในระบบคือ `splitType = split_half`

### 2.4 คืนเต็มจำนวน

คือรายการที่อีกคนต้องคืนเต็มจำนวน

- ในระบบคือ `splitType = full_reimburse`

### 2.5 ผ่อน

คือรายการผ่อนรายเดือน

- ถ้าตั้งต้นว่า “หารร่วม” ก็ต้องหารต่อทุกงวดจนจบ
- ถ้าตั้งต้นว่า “ไม่หาร” ก็ต้องคงแบบนั้นไปจนจบเช่นกัน

## 3. กติกาการคำนวณที่ตกลงกัน

## 3.1 ค่าอาหารที่คนไม่ได้ถือกระเป๋าจ่าย

ถ้าค่าอาหารถูกจ่ายโดยคนที่ไม่ได้ถือกระเป๋าอาหาร

- คนถือกระเป๋าต้องคืนเงินให้เต็มจำนวน
- ไม่ใช่คืนครึ่งเดียว

ความหมายแบบคนทั่วไป

- ถ้ารอบนี้ `Champ` ถือกระเป๋าอาหาร
- แต่ `Lily` ออกค่าอาหารเอง 120 บาท
- ระบบต้องนับเป็น `Champ ให้ Lily 120`

ในหน้า settlement รายการแบบนี้จะขึ้นเหตุผลประมาณ

- `ค่าอาหารที่จ่ายโดยคนที่ไม่ได้ถือกระเป๋า`

## 3.2 ค่าใช้จ่ายร่วมแบบหารครึ่ง

ถ้ารายการเป็นค่าใช้จ่ายร่วม

- คนที่ไม่ได้จ่าย ต้องคืนคนที่จ่าย “ครึ่งหนึ่งของรายการ”

ตัวอย่าง

- Lily จ่ายของใช้ร่วมบ้าน 350
- ระบบต้องนับเป็น `Champ ให้ Lily 175`

## 3.3 รายการคืนเต็มจำนวน

ถ้ารายการถูกตั้งเป็นคืนเต็มจำนวน

- คนที่ได้ประโยชน์จากรายการนั้น ต้องคืนเต็มจำนวนให้คนที่จ่าย

## 3.4 ผ่อนชำระ

ถ้าตอนสร้างรายการผ่อน ตั้งว่า “หาร”

- ต้องหารแบบเดิมทุกงวดจนกว่าจะหมด

ห้ามเปลี่ยนกติกากลางทางเองจากการคำนวณของระบบ

ตัวอย่าง

- `รถ 8/60`
- `Apple watch 7/24`

ถ้ารายการตั้งต้นเป็นผ่อนแบบหารร่วม

- แต่ละงวดต้องสร้างยอดหารครึ่งต่อไปเรื่อย ๆ จนจบงวดสุดท้าย

## 3.5 เงินอาหารคงเหลือ

ถ้ารอบนั้นใช้เงินอาหารไม่หมด

- ให้ “ยกทั้งก้อน” ไปเป็นเงินตั้งต้นของรอบถัดไป
- ไม่ใช่หารครึ่งก่อนค่อยยกไป

ตัวอย่าง

- รอบนี้เหลือ 2,000
- รอบถัดไปต้องเริ่มด้วย carry over = 2,000

## 3.6 เงินอาหารเกินงบ

ถ้ารอบนั้นใช้ค่าอาหารเกินงบ

- ให้ถือว่าเป็นภาระร่วม
- คนที่ไม่ได้ถือกระเป๋าอาหาร โอนคืนให้คนถือกระเป๋า “ครึ่งหนึ่งของยอดที่เกิน”

ตัวอย่าง

- งบอาหารรอบนี้ 10,000
- ใช้จริง 13,266
- เกินงบ 3,266
- ต้องมีรายการ `ค่าอาหารเกินงบรอบนี้ = 1,633`

เหตุผล

- เพราะส่วนที่เกินเป็นค่าอาหารร่วมกันของทั้งคู่
- จึงต้องหารกันคนละครึ่ง

## 3.7 เงินเติมค่าอาหารรอบถัดไป

หลังจบรอบ ต้องดูว่ารอบถัดไปต้องเติมเงินเข้ากระเป๋าอาหารอีกเท่าไร

สูตรความหมายแบบคนทั่วไป

- เอา “งบรอบถัดไปที่ต้องการ”
- ลบด้วย “เงินอาหารที่ยกไปได้จากรอบก่อน”
- ถ้ายังขาดอยู่ ให้คนที่ไม่ได้ถือกระเป๋าโอนให้คนถือกระเป๋า “ครึ่งเดียวของยอดที่ต้องเติม”

ตัวอย่าง

- งบรอบถัดไปตั้งไว้ 10,000
- เงินคงเหลือยกไปได้ 0
- แปลว่าต้องเติมเพิ่ม 10,000
- คนที่ไม่ได้ถือกระเป๋าโอนให้คนถือกระเป๋า 5,000

สรุปสั้น ๆ

- ระบบไม่ควรบังคับให้อีกคนโอนเต็ม 10,000
- ควรโอนแค่ครึ่งเดียวของยอดที่ต้องเติม

## 4. ลำดับการคิดยอดในหนึ่งรอบ

ระบบควรคิดตามลำดับนี้

1. รวมค่าอาหารทั้งหมดของรอบ
2. รวมค่าใช้จ่ายร่วม
3. รวมรายการคืนเต็มจำนวน
4. รวมรายการผ่อน โดยยึด split เดิมของรายการผ่อนนั้น
5. คำนวณว่าอาหารเหลือหรือเกินงบ
6. ถ้าเกินงบ ให้เพิ่มยอดหารครึ่งของส่วนเกิน
7. คำนวณว่ารอบถัดไปต้องเติมเงินอาหารเพิ่มอีกเท่าไร
8. ให้คนที่ไม่ได้ถือกระเป๋าโอนครึ่งหนึ่งของยอดที่ต้องเติมให้คนถือกระเป๋า
9. รวมยอดสองฝั่งแล้วหักลบเป็นยอดสุทธิ

## 5. ตัวอย่างอ้างอิงจากรอบ 2026-05-25 ถึง 2026-06-24

รอบนี้เป็นตัวอย่างอ้างอิงที่เราใช้คุยและตรวจความเข้าใจร่วมกันจากภาพหน้า settlement

ค่าหลักบนหน้าจอ

- `Champ ให้ Lily = 10,115`
- `Lily ให้ Champ = 21,626`
- `หลังหักลบ = Lily ให้ Champ 11,511`
- `งบทั้งหมด = 10,000`
- `ค่าอาหารคงเหลือ = -3,266`
- `เติมรอบถัดไป / คน = 5,000`

ความหมายของตัวเลขสำคัญ

### 5.1 ค่าอาหารคงเหลือ `-3,266`

แปลว่า

- ใช้ค่าอาหารเกินงบ 3,266
- ส่วนเกินนี้ต้องหารครึ่ง
- จึงเกิดยอด `ค่าอาหารเกินงบรอบนี้ = 1,633`

### 5.2 เงินเติมค่าอาหารรอบถัดไป `5,000`

แปลว่า

- รอบนี้ไม่มีเงินเหลือให้ยกไป
- รอบถัดไปต้องการงบ 10,000
- คนที่ไม่ได้ถือกระเป๋าโอนให้คนถือกระเป๋า 5,000

### 5.3 รายการผ่อนในตัวอย่าง

จากภาพมีรายการเช่น

- `Apple watch 7/24 = 310`
- `รถ 8/60 = 6,860`

รายการเหล่านี้สะท้อนกติกาว่า

- ถ้าตั้งต้นว่าเป็นผ่อนแบบหารร่วม
- งวดนั้นต้องถูกนับเข้าฝั่ง settlement ตามสัดส่วนเดิม

### 5.4 ยอดสุทธิ

เอา 2 ฝั่งมาหักลบกัน

- `21,626 - 10,115 = 11,511`

จึงได้ผลสุดท้าย

- `Lily ให้ Champ 11,511`

## 7. กฎที่ห้ามเพี้ยนในอนาคต

ถ้ามีการแก้ logic settlement ต้องระวังไม่ให้กฎต่อไปนี้เพี้ยน

- ค่าอาหารที่คนไม่ได้ถือกระเป๋าจ่าย ต้องคืนเต็มจำนวน
- เงินอาหารเหลือ ต้องยกทั้งก้อนไปรอบถัดไป
- เงินอาหารเกินงบ ต้องหารครึ่ง
- เงินเติมรอบถัดไป คนที่ไม่ได้ถือกระเป๋าโอนแค่ครึ่งเดียวของยอดที่ต้องเติม
- รายการผ่อนต้องยึด split เดิมไปจนจบงวด

## 8. ถ้าจะเปลี่ยนกติกาในอนาคต

ถ้าจะเปลี่ยนกติกาธุรกิจ ต้องตอบให้ได้ก่อนเสมอว่า

1. เปลี่ยนเฉพาะรอบใหม่ หรือย้อนกระทบรอบเก่าด้วย
2. เปลี่ยนเฉพาะวิธีแสดงผล หรือเปลี่ยนวิธีคำนวณจริง
3. รายการผ่อนที่สร้างไปแล้ว ต้องแปลงตามกติกาใหม่หรือคงของเดิม
4. ค่าอาหารเกินงบและเงินเติมรอบถัดไป จะยังหารครึ่งเหมือนเดิมหรือไม่

ถ้ายังตอบ 4 ข้อนี้ไม่ครบ ไม่ควรแก้ logic settlement ทันที
